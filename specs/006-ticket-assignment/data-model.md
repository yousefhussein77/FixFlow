# Data Model: Ticket Assignment

## Ticket (existing, extended)

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | positive integer | yes | Existing internal key |
| `reference` | string, max 16 | yes | Existing unique immutable public identifier |
| `reporter_id` | user reference | yes | Existing reporter; restricted on deletion |
| `department_id` | department reference | yes | Existing classification |
| `category_id` | category reference | yes | Existing classification |
| `title` | string, max 160 | yes | Existing trimmed ticket title |
| `priority` | enum | yes | Existing `low`, `medium`, `high`, or `urgent` |
| `status` | string, max 30 | yes | Existing `new`; this feature adds valid `assigned` state |
| `assigned_technician_id` | user reference | no | New; null while unassigned, otherwise one current technician; restricted on deletion |
| `created_at` | timestamp | yes | Existing; newest-first primary ordering |
| `updated_at` | timestamp | yes | Existing; changes once on accepted assignment only |

Other existing ticket fields and photo relationships remain unchanged.

### Relationships

- Belongs to one reporter, department, and category.
- Belongs optionally to one current assigned technician through `assigned_technician_id`.
- Has zero or more immutable status-history rows in chronological order.

### Assignment invariants

- `status = new` implies `assigned_technician_id = null` for all outcomes produced by approved
  features through this point.
- An assignment can be created only when the locked ticket is `new` and
  `assigned_technician_id IS NULL`.
- An accepted assignment produces `status = assigned` and a non-null active technician reference in
  the same transaction as exactly one history insert.
- A rejected, conflicting, unauthorized, or failed assignment changes no ticket field, including
  `updated_at`.
- No operation in this feature clears or replaces `assigned_technician_id`.

### Indexes and constraints

- Foreign key `assigned_technician_id -> users.id` with restricted deletion.
- Index `assigned_technician_id` to support responsibility lookup without adding a technician queue.
- Preserve existing unique reference, reporter/submission-token uniqueness, and reporter list index.
- Application validation restricts state transitions; the database foreign key protects referential
  integrity. Role and active-state checks remain transactional business invariants because they can
  change over time.

## Ticket Status History (new)

Append-only record of the one accepted assignment transition. No update or delete operation is
exposed by this feature.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `id` | positive integer | yes | Internal immutable key |
| `ticket_id` | ticket reference | yes | Parent ticket; restricted on deletion |
| `from_status` | string, max 30 | yes | Exactly `new` in this feature |
| `to_status` | string, max 30 | yes | Exactly `assigned` in this feature |
| `actor_id` | user reference | yes | Active administrator who accepted the action; restricted on deletion |
| `assigned_technician_id` | user reference | yes | Technician selected by the accepted action; restricted on deletion |
| `occurred_at` | timestamp | yes | Canonical server-side assignment time |
| `created_at` | timestamp | yes | Persistence time; generated by the server |

### Relationships and indexes

- Belongs to one ticket, one acting administrator, and one assigned technician.
- Index `(ticket_id, occurred_at, id)` for stable chronological history.
- Index `actor_id` and `assigned_technician_id` for integrity and operational investigation.
- No `updated_at` field is needed because history is immutable.

### Validation invariants

- `actor_id` resolves to the authenticated active administrator at commit time; it is never accepted
  from request input.
- `assigned_technician_id` matches the ticket's newly stored current technician.
- The selected user exists, is active, and has role `technician` at commit time.
- The history transition and ticket mutation are committed or rolled back together.
- Exactly one history row is created for the one accepted initial assignment.

## User (existing, unchanged)

| Relevant field | Rule |
|---|---|
| `id` | Identifier used by assignment and option contracts |
| `name` | Only user attribute returned by technician options and ticket summaries |
| `role` | Existing enum; eligibility requires exactly `technician`; action authority requires `administrator` |
| `is_active` | Existing boolean; both administrator action and technician eligibility require true |

No user-management schema or endpoint is added. The option lookup returns only active technicians;
the assignment transaction treats cached option data as untrusted and reloads current user state.

## Read Models

### Administrator ticket summary

Composed from Ticket plus existing relationships; it is not a separate persisted entity.

- `reference`, `title`, `priority`, `status`, `created_at`
- reporter `{id, name}`
- department `{id, name}`
- category `{id, name}`
- assigned technician `{id, name}` or explicit `null`

### Technician option

Minimal non-persisted projection `{id, name}` over users satisfying `is_active = true` and
`role = technician`, ordered by name then id. It conveys availability for selection, not authority.

## State Transition

```text
new + no technician
        |
        | active administrator chooses active technician;
        | locked transaction revalidates both records
        v
assigned + one technician + one immutable history row
```

All other transitions are invalid in this feature. `assigned` is terminal with respect to these
operations: reassignment, unassignment, processing, completion, rejection, and deletion are deferred.

## Transaction Sequence

1. Authenticate active administrator before any target resolution.
2. Start a database transaction and query the ticket within the oversight boundary for update.
3. Return concealed `404` if no permitted ticket resolves.
4. While holding the lock, reject with `409` unless status is `new` and assignee is null.
5. Resolve the submitted user and verify current active technician eligibility; reject with `422` on
   unknown, inactive, or wrong-role input.
6. Set `assigned_technician_id`, set status `assigned`, and insert one matching history row.
7. Commit and return an eagerly loaded authoritative administrator ticket summary.

Any exception rolls back both writes. A competing transaction sees the committed state after acquiring
the lock and returns `409` without an additional ticket update or history row.
